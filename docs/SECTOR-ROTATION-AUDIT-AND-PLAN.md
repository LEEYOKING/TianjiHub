# 天机枢 · 板块轮动 — 技术审计结论与开发规划

> 本文基于对现有仓库（`TJHUB天机枢`）的真实代码/数据审计 + 对外部数据接口的实测验证写成。
> 目标：回答三个问题 —— **现有接口够不够？要不要数据库？要不要 AI？** 并给出产品设计与分期开发规划。

---

## 0. 结论摘要（先看这里）

| 问题 | 结论 | 一句话理由 |
| --- | --- | --- |
| **现有数据接口能满足需求吗？** | **部分能，缺口明确** | 当日板块涨跌已有；**历史每日序列完全没有**，但**可用东财板块日线接口补齐，无需引入新数据源** |
| **需要数据库吗？** | **V1 不需要** | 按 V1 范围约 6.6 万～16.6 万行，紧凑 JSON 完全装得下；规则引擎放前端计算，毫秒级。只有当"超长历史 / 多用户 / 服务端统计"出现时才需要 D1 |
| **需要接入 AI 吗？** | **V1 不需要，V2 可选** | PRD 里"系统自动生成的描述"本质是**确定性模板文本**，用规则引擎生成更准、可复现、零成本；AI 只适合做 V2 的"自然语言解读层"，且必须喂结构化统计、不得输出买卖信号 |

**最重要的一个发现**：东财板块日线接口 `push2his` 对每个板块返回**完整历史日线**（实测 `银行Ⅱ` 返回 **6484 根、从 2000-01-04 至今**，含涨跌幅/成交额/换手率）。这意味着"历史归档"这一层的**采集端零新建**，只是现在没抓而已。

## 1. 现状审计（决定要不要新建基础设施）

### 1.1 现有架构

```
GitHub Actions（cron: 北京 15:35 / 18:35 / 08:30）
      ↓  Python 脚本（akshare + 腾讯/东财/同花顺直连）
      ↓  生成 JSON 并提交回仓库
Cloudflare Pages（纯静态，git 集成自动重新构建）
      ↓  浏览器直接读 /data.json 等静态文件
```

关键事实：

- `wrangler.toml` 仅作项目标识，**无 Cloudflare Workers、无 D1、无 Functions**（历史 Functions 已删除）。
- 全部"计算"发生在**两个位置**：Python 批处理（离线）、React 前端（运行时）。
- 因此**任何新增功能，要么进批处理、要么进前端**；要"服务端按需计算"就必须新建 Worker —— 这是判断要不要 D1 的前提。

### 1.2 现有板块数据（对照需求）

| 需求要求 | 现状 | 结论 |
| --- | --- | --- |
| 每个交易日 × 每个板块 的涨跌幅 | `data.json` 的 `sectors/conceptSectors/regionSectors` 只有**当日快照**（90 + 30 + 16 条） | ❌ **缺口：无历史序列** |
| 板块稳定唯一 ID | 现有只有 `name`（有的带 `leaderCode`），**不存板块 BK 码** | ❌ **缺口：无稳定主键**（PRD 明确要求不要用名称做主键） |
| 板块成交额 | 有 `totalTurnover`（当日） | ⚠️ 仅当日 |
| 板块分类（行业/概念/地域） | 有（三个数组） | ✅ |
| 板块指数日线 | `sectorKlines.json` 是**领涨股**的 K 线（61 日），**不是板块指数** | ❌ 不可用于轮动 |
| 交易日历 | Python 脚本已用 `ak.tool_trade_date_hist_sina()`；前端有 `meta.nextTradeDate` | ✅ 可复用 |
| 市场基准（宽基指数） | 已有 7 个指数（上证/深证/创业板/北证50/科创50/沪深300/微盘） | ✅ 可复用做相对强度 |

**一句话**：现在系统里**没有任何"板块历史"**，只有"今天的板块"。这是唯一但也是最大的缺口。

### 1.3 历史数据可取性（已实测，非推测）

**接口**：东财板块日线

```
GET https://push2his.eastmoney.com/api/qt/stock/kline/get
    ?secid=90.{板块BK码}
    &fields1=f1,f2,f3,f4,f5,f6
    &fields2=f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61
    &klt=101&fqt=0&beg=0&end=20500101&lmt={条数}
```

实测结果：

| 项 | 实测值 |
| --- | --- |
| 样本 | `secid=90.BK0475`（银行Ⅱ） |
| 返回条数 | **6484 根** |
| 起始日期 | **2000-01-04** |
| 末根示例 | `2026-10-13,4457.95,4430.33,4463.09,4413.83,19605163,15777244877.00,1.10,-0.67,-30.02,0.15` |

字段映射（已核对数值自洽）：

| 序号 | 字段 | 含义 |
| --- | --- | --- |
| f51 | date | 交易日 |
| f52 / f53 | open / close | 开 / 收 |
| f54 / f55 | high / low | 高 / 低 |
| f56 | volume | 成交量（手） |
| f57 | amountAmount | 成交额（元） |
| f58 | amplitude | 振幅 % |
| **f59** | **changePct** | **涨跌幅 %** ← 轮动核心字段 |
| f60 | changeAmount | 涨跌额 |
| f61 | turnoverRate | 换手率 % |

**板块池规模**（实测 `push2.eastmoney.com/api/qt/clist/get`）：

| 板块类型 | `fs` 参数 | 实测数量 |
| --- | --- | --- |
| 地域 | `m:90+t:1` | **31** |
| 行业 | `m:90+t:2` | **496**（申万一/二/三级混合） |
| 概念 | `m:90+t:3` | **506** |
| 合计 | — | **1033** |

采集成本评估：

- **一次性回补**：每板块 1 次请求 → 665～1033 次请求，串行约 **5～10 分钟**（批处理可接受）。
- **日常增量**：无需逐板块请求 —— 现有 `fetchEMIndustries` 系列已经用 **1 次 clist 请求**拿到全部板块的当日涨跌幅/成交额，直接追加一行即可。

> ⚠️ 风险：东财对海外/云 IP 间歇性封锁（此前 9/30 就整晚不可用）。批处理必须沿用项目已有的**多域名轮询 + 重试**模式，并对同花顺做兜底（同花顺板块历史接口实测当前 SSL 不稳定，建议仅作兜底而非主源）。

## 2. 数据层方案

### 2.1 建议的板块池（V1）

要与现有页面口径一致，避免"同一个板块两个页面名字不一样"：

| 类型 | V1 建议池 | 数量 | 理由 |
| --- | --- | --- | --- |
| 行业 | 申万二级（与【板块涨跌】页 `live.ts` 的 128 个名单一致） | 128 | 既有页面已用二级口径，且用户已确认过该粒度 |
| 概念 | 东财概念全量（可按样本数过滤，见下） | ≤506 | 概念轮动是短线交易者核心关注点，现有页面只有 30 个太少 |
| 地域 | 东财地域 | 31 | 与现有页面一致 |

**过滤建议**：概念板块剔除成分股 < 5 只的，避免"3 只股票的板块"霸榜。

### 2.2 存储格式：紧凑列式 JSON（不上数据库）

因为前端要"改一个滑块就重算全窗口"，最省事的做法是把**原始行情一次性送到前端**，把计算留在浏览器。

```jsonc
// public/rotation.json  (V1 建议按窗口分片: rotation-90.json / rotation-250.json)
{
  "meta": {
    "generatedAt": "2026-10-13 18:42:10",
    "lastTradeDate": "2026-10-13",
    "windows": [90, 250],
    "sectorCount": 665,
    "benchmark": "sh000300",       // 相对强度基准
    "calendarSource": "sse"
  },
  "dates": ["2026-06-03", "..."],   // 全局交易日索引(升序) — 所有板块共用
  "bench":  [-0.42, 0.31, "..."],   // 基准指数每日涨跌幅,与 dates 对齐
  "sectors": [
    {
      "id": "BK0475",               // ← 稳定主键(东财板块码)
      "name": "银行Ⅱ",
      "type": "industry",           // industry | concept | region
      "pct": [-0.67, 1.99, "..."],  // 每日涨跌幅 %,长度=dates.length,缺失位用 null
      "amt": [157.77, 362.79, "..."],// 每日成交额(亿),缺失位用 null
      "stockCount": 42              // 用于过滤/覆盖率说明
    }
  ]
}
```

体积估算（`pct` + `amt` 各按 ~7 字符/值计）：

| 方案 | 板块数 × 天数 | 原始 | gzip 后 |
| --- | --- | --- | --- |
| 行业 128 + 地域 31，250 日 | 159 × 250 × 2 | ≈ 0.6 MB | **≈ 0.15 MB** |
| V1 全量 665 板块 × 90 日 | 665 × 90 × 2 | ≈ 0.9 MB | **≈ 0.25 MB** |
| V1 全量 665 板块 × 250 日 | 665 × 250 × 2 | ≈ 2.4 MB | **≈ 0.7 MB** |

结论：**V1 完全不需要数据库**。即便全量 250 日，gzip 后也只有几百 KB，且只在进入【板块轮动】页时按需加载（不影响其他页面首屏）。

### 2.3 为什么 V1 不上 D1（以及什么时候该上）

D1 的三个真实价值点，对照当前需求：

| D1 的价值 | V1 是否需要 | 说明 |
| --- | --- | --- |
| 存超长历史（数年 × 千板块） | ❌ 不需要 | V1 只要 90/250 日；真要做"26 年全历史回测"再考虑（那也优先考虑按年分片 JSON 而非 D1） |
| 多用户保存规则方案 | ❌ 不需要 | 当前是单用户静态站点。V1 规则可用 `localStorage` + "复制配置串"分享实现（PRD 的"复制当前配置"就是这个思路） |
| 服务端按需统计/回测 | ❌ 不需要 | 665 板块 × 90 日 = 6 万个数据点，前端 JS 全窗口重算 < 10 ms，比网络往返还快 |

**触发升级 D1 的条件（满足任一）**：
1. 需要 ≥ 3 年历史做样本外回测；
2. 需要跨用户共享/云端保存规则集；
3. 需要服务端定时跑"全板块 × 多规则"的事件预计算（组合爆炸，前端算不动）。

若将来上 D1，表结构直接采用 PRD 第五章的 8 张表（`trade_calendar` / `sectors` / `sector_daily_quotes` / `rotation_rule_sets` / `sector_daily_events` / `sector_event_clusters` / `sector_window_stats` / `data_sync_jobs`），索引为 `(trade_date, sector_id)` 与 `(sector_id, trade_date)`。按 V1 量级估算：665 板块 × 250 日 ≈ **16.6 万行**，远低于 D1 免费额度（500 万行读/日、10 万行写/日、5 GB 存储），但**当前没必要付这份复杂度**。

### 2.4 数据更新机制（复用现有链路）

| 环节 | 做法 |
| --- | --- |
| 一次性回补 | 新增 `scripts/fetch_rotation.py --backfill --days 250`，逐板块拉日线，写入 `rotation.json`。**手动跑一次** |
| 每日增量 | 在现有 18:35 那档 cron 里，用**已有的 clist 快照**追加当日一行（零新增请求） |
| 完整性校验 | ① 板块数环比突变告警；② 日期与 `trade_calendar` 对齐（不缺交易日）；③ 空值/`null` 统计；④ `|pct| > 20%` 异常告警 |
| 补数 | 支持 `--from 2026-09-01 --to 2026-09-30` 按区间重算覆盖（幂等：以 `(date, sector_id)` 为键 upsert） |
| 覆盖率 | 每个板块记录有效日数，页面上标注"数据覆盖率"，缺失日**不计为 0 涨跌**（PRD 第 8 章明确要求） |

> 沿用项目已有的踩坑经验：脚本必须支持"数据源陈旧/封锁时**不写脏数据**"（同 `fetch_real_data.py` 里那条 `nextTradeDate` / 陈旧值校验逻辑的思路）。

## 3. 计算层方案（规则引擎 + 算法 A–H）

### 3.1 分层原则（PRD 反复强调的一点）

```
rotation.json   ← 事实层：原始行情，永不因规则改变而重写
      ↓
事件层           ← 派生：rank_up / rank_down / large_up / large_down / strong / weak
      ↓
统计层           ← 派生：次数、频率、间隔、连续性、事件簇、收益/回撤/相对强度
      ↓
展示层           ← 依赖"当前规则"，所有模块共用同一份 ruleSet 快照
```

实现要点：

- 规则用**单一对象**贯穿所有视图（`RuleSet`），组件不得各自读阈值 —— 这是"改一个滑块后各模块口径不一致"的根本解法。
- 规则可序列化为字符串（`复制当前配置`），便于分享与版本留痕（PRD 的 `rule_version`）。
- 事件层与统计层做成**纯函数 + 记忆化**（`useMemo`）：滑块变化只重算派生层，不动原始数据。

### 3.2 前端计算性能（已按量级核算）

| 场景 | 计算量 | 预期耗时 |
| --- | --- | --- |
| 改 TOP N / 阈值 → 重算 665 板块 × 90 日事件 | ≈ 6 万次比较 | < 5 ms |
| 重算间隔/连续/回撤等统计 | ≈ 6 万次算术 | < 10 ms |
| 90 日全屏时间轴重绘（665 × 90 格） | 需**虚拟化/降采样**（见下） | 见 4.2 |

### 3.3 需要落到产品口径的 8 条规则（PRD 第 8 章已列，这里补实现细节）

| 项 | 实现口径（建议） |
| --- | --- |
| 统计窗口 | 近 N 个**有效交易日**（分母 = 该板块有效数据日数） |
| 排名并列 | 排序键 `(changePct DESC, sectorId ASC)` —— 保证同样数据每次排序结果一致 |
| 大涨/大跌 | 支持 幅度 / 排名 / 组合 三种模式；**关闭的条件不得隐含生效** |
| 间隔单位 | **交易日序号差**（相邻两事件日 `Δ=1` 表示相隔 1 个交易日步长），UI 必须写清定义 |
| 连续事件 | 按交易日判断；且必须与"连续上涨"分开（连续进榜 ≠ 连续上涨） |
| 独立事件簇 | 冷却期规则：`距最近已归属事件日 ≤ X 步长` 则并入同簇；**簇间隔用簇起始日相减**（不要拿簇尾比簇头） |
| 累计收益 | 复合收益 `∏(1+r)-1`，不可直接相加 |
| 样本不足 | **间隔数 < 4 时只展示原始数据并标注"样本不足"**，不给集中度百分比 |

## 4. 产品设计（前端）

### 4.1 侧栏结构改造

现有侧栏是**扁平 9 项**（`Layout.tsx` 的导航数组）。新增"大板块"需要引入**分组导航**：

```
天机枢
├─ 大盘总览        /overview
├─ 板块涨跌        /sector        （现有，当日快照）
├─ 板块轮动 ★新增   ├─ /rotation           轮动档案(总览)
│                  ├─ /rotation/timeline  轮动时间轴
│                  └─ /rotation/sector/:id 板块行为详情
├─ 连板天梯 / 跌停梯队 / 放量突破 / 突破前高 / 低位放量 / 龙虎榜
└─ 全景手术台 / 隔夜数据
```

实现方式：导航数组加 `group` 字段，分组可折叠；路由保持扁平注册（React Router 现有结构不用改），新增 4 条路由。

### 4.2 四个界面

**① 轮动档案（总览）** — 对应示例图 1 的"三层"叙事

- 第一层「每日强弱榜档案」（基础层）：最新交易日的强势榜 / 弱势榜 TOP N，卡片直接显示板块名 + 涨跌幅。
- 第二层「板块行为画像」（核心层）：4 个入口卡（反复活跃次数 / 活跃间隔 / 涨跌交替 / 趋势与持续性），点击进入详情。
- 第三层「板块轮动关系」（进阶层）：同步活跃、先后关系、市场环境分层的入口（V1.2/V2 落地）。
- 顶部常驻**「当前规则摘要」条** + **数据覆盖率**提示。

**② 轮动时间轴** — 横轴交易日、纵轴板块，格子着色（强势/弱势/大涨/大跌）

- **性能约束**：665 × 90 = 6 万格，直接渲染不可行。方案：默认只渲染 TOP 活跃板块（可调 20/50/100）；**用 Canvas 网格绘制，不用 DOM**；支持按板块类型/规则/窗口切换。
- 每个格子**可点击** → 弹出解释（"当日涨幅 +4.2%，排名第 3，命中：进榜 AND 阈值 ≥3%"）。这是 PRD 特别强调的**可解释性**，必须做。

**③ 板块行为详情** — 对应示例图 2

- 指标区：强势/弱势出现次数、平均间隔/中位间隔、最近一次强势距今交易日、当前连续强势/历史最长、累计收益/波动率/最大回撤、相对基准强度、覆盖率。
- 事件时间轴：N 格彩色条（绿=进强势榜 / 红=进弱势榜 / 灰=未进榜），下方标注日期序号。
- 「系统自动生成的描述」区块（见第 5 章，**模板生成，非 AI**）。
- 「计算口径」折叠区：把当前规则、样本数、公式原样列出。

**④ 规则配置器** — 抽屉式，分三区（PRD 建议）

- 基础设置：窗口（15/30/60/90）、板块范围（全部/仅行业/仅概念/仅地域）、TOP N（5/10/20）
- 事件定义：大涨阈值、大跌阈值、是否要求进榜、组合方式（AND/OR）
- 高级统计：事件间隔区间 [min,max]、冷却期、相对强度基准
- 底部：`复制当前配置` / `重置默认` / 实时规则摘要

样式沿用现有体系：`CARD_SHADOW`、圆角 14px、`COLOR_UP/COLOR_DOWN/COLOR_FLAT`，`PageHeader` 复用，移动端 `isMobile` 响应式（随时间轴横向滚动）。

## 5. AI 是否需要接入？如何接入？

### 5.1 V1：不接入，用模板引擎（推荐）

PRD 示例里那段"系统可以自动生成的描述"：

> 最近 20 个交易日，进入强势榜 5 次，进入弱势榜 2 次。
> 强势事件发生在第 3、4、8、12、16 天，事件间隔分别为 1、4、4、4 个交易日。
> 强势事件集中在后半段以外的多个时点，并非单次连续上涨。

这**完全是结构化统计的文本化**，用模板即可 100% 准确产出：

```ts
// 伪代码：确定性描述生成器
lines.push(`最近 ${D} 个交易日，进入强势榜 ${kUp} 次，进入弱势榜 ${kDown} 次。`);
if (gaps.length) {
  lines.push(`强势事件发生在第 ${eventDays.join('、')} 天，事件间隔分别为 ${gaps.join('、')} 个交易日。`);
}
if (gaps.length < 4) lines.push(`⚠ 间隔样本仅 ${gaps.length} 个，不足以判断规律。`);
```

理由（也是给用户的风险控制）：

1. **可复现**：同样的数据 + 同样的规则 → 同样的文字，可审计；
2. **零成本零延迟**：不调 API、不等待、不怕限流；
3. **不会幻觉**：数字全部来自已计算字段，AI 有编造数字的风险；
4. 与"统计结果透明可解释"的产品原则一致。

### 5.2 V2（可选）：AI 只做"解读层"，且喂结构化结果

若确实想要"更像分析师口吻的点评"，建议这样接：

| 维度 | 方案 A（推荐）**批处理预生成** | 方案 B（不推荐首选）运行时 Worker |
| --- | --- | --- |
| 位置 | 现有 GitHub Actions 脚本里，盘后调用一次 LLM API | 新建 Cloudflare Worker，前端按需请求 |
| 输入 | **只用已算好的结构化统计**（次数/间隔/连续性/收益/回撤/相对强度 JSON），**不喂原始行情** | 同左 |
| 输出 | `rotation-insight.json`（静态文件，前端直接读） | 流式返回 |
| 成本/依赖 | 每天 1 次调用；无运行时依赖、无密钥下发 | 需 Worker + 密钥管理 + 限流 + 费用不可控 |
| 失败影响 | 生成本次跳过，页面自动回落模板描述 | 页面出现加载/报错态 |
| 合规 | 结果落库可审计、可回溯 | 需额外日志 |

**必须遵守的红线**（写进 UI 与文案）：

- 明确标注"**机器生成的辅助解读，不是买卖信号**"；
- **不得**输出目标价、买卖点、仓位建议；
- **不得**把"历史频率"表述为"未来概率"；
- 所有 AI 文本不可覆盖/替代可解释的原始指标，只能作为附加区块。
